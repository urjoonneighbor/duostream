# DuoStream — приватный P2P-стрим и голосовой чат на двоих

Стример показывает экран или окно игры, зритель смотрит, оба разговаривают голосом.
Видео и звук идут **напрямую между двумя ПК** (WebRTC, DTLS-SRTP). Сервер нужен только
для рукопожатия: обмена SDP и ICE-кандидатами. Облака, базы данных и платные API не используются.

| | |
|---|---|
| Видео | захват экрана/окна, 1920×1080 или 2560×1440, **120 FPS** (собственный захват WGC), 8–20+ Мбит/с |
| Кодек | **AV1 на NVENC** (через Media Foundation), запасные H.264 и VP9, автопереключение |
| Голос | Opus 64 кбит/с + FEC, локальный шумодав **DeepFilterNet3 (48 кГц, класса Krisp) на ONNX Runtime** + голосовой порог по распознавателю речи **Silero VAD** (глушит скрип, шмыганье, дыхание между фразами) |
| Управление | глобальные горячие клавиши (в игре тоже): микрофон, звук, рация (push-to-talk), шумодав, трансляция |
| Чат | сообщения и файлы любого размера напрямую P2P (каналы данных WebRTC), докачка после переподключения |
| Оверлей | поверх игры: микрофон, кто говорит, стрим, сообщения; не попадает в трансляцию |
| Журнал | файл на день (`%APPDATA%\DuoStream\logs`), прошлые дни — в `.gz`, хранятся 30 дней; у зрителя — картинки кадров-выбросов |
| Звук стрима | окно — звук только его приложения (Windows Process Loopback), экран — системный звук без звуков DuoStream; Opus-стерео, по желанию |
| Сеть | P2P; белый IP и проброшенные порты у стримера, зритель может быть за серым NAT/CGNAT |
| Приложение | Electron 44 (Chromium 152), Windows 10/11 x64; сборка и обновления — GitHub Actions + Releases |

## Архитектура

```
        ПК стримера (белый статический IP, порты проброшены)                 ПК зрителя (серый NAT)
 ┌──────────────────────────────────────────────────────────┐        ┌─────────────────────────────┐
 │  server/  Node.js + ws  ◄── TCP 8787 (WebSocket) ────────┼────────┼──  client/ (Electron)        │
 │   • пароль: challenge–response (PBKDF2 + HMAC)           │ сигнали-│   • роль «зритель»          │
 │   • пересылает SDP/ICE, ничего не хранит                 │ зация   │   • AV1-декодер (D3D11)     │
 │        ▲ ws://127.0.0.1:8787                             │        │   • микрофон → шумодав      │
 │  client/ (Electron), роль «стример»                      │        │                             │
 │   • duostream-capture.exe: WGC 1 мс → D3D-текстуры       │        │                             │
 │     → sharedTexture → VideoFrame (GPU) → AV1 NVENC       │ медиа  │                             │
 │   • микрофон → AudioWorklet → DFN3/ONNX → Opus  ◄════════╪═ UDP ══╪═► P2P, DTLS-SRTP            │
 │   • WebRTC на UDP 50000–50019 (проброшены на роутере)    │ 50000+ │   (никаких серверов между)  │
 └──────────────────────────────────────────────────────────┘        └─────────────────────────────┘
                     STUN stun.l.google.com:19302 — только чтобы узнать внешний адрес
```

**Как зритель за CGNAT достаёт до стримера.** Приложение стримера ограничивает WebRTC диапазоном
UDP 50000–50019 (`setWebRTCUDPPortRange`), а роутер пробрасывает этот диапазон на ПК. Chromium про
проброс не знает, поэтому стример сам добавляет ICE-кандидат `<белый IP>:<порт host-кандидата>`.
Зритель отправляет на него пакеты, стример отвечает на адрес, с которого они пришли, — соединение
устанавливается при любом типе NAT у зрителя, без TURN. Белый IP берётся из STUN или из настройки.

**Как получаются 120 FPS.** Встроенный захват Chromium на Windows 11 24H2+ выдаёт не больше ~60 FPS:
Windows Graphics Capture по умолчанию отдаёт кадр не чаще раза в 16 мс, а Chromium это не меняет
(подробности — в «Ограничениях»). Поэтому у стримера работает отдельный процесс
`duostream-capture.exe` (C#, .NET): он захватывает экран или окно через WGC с `MinUpdateInterval = 1 мс`
и копирует кадр на GPU в кольцо общих D3D11-текстур (~0,2 мс на кадр). Electron импортирует текстуру
модулем `sharedTexture`, и она попадает в WebRTC как `VideoFrame` через `MediaStreamTrackGenerator`, без
копирования в оперативную память. Если процесс захвата не собран, не запустился, упал или кадры не
пошли — приложение само переключается на встроенный захват Chromium (до ~60 FPS).

**Безопасность.** Сигнальный сервер пускает только по общему паролю (пароль по сети не передаётся),
банит IP после 5 неудачных попыток. Каждое сигнальное сообщение подписывается HMAC общим паролем
и проверяется у собеседника: подменить SDP (а значит, DTLS-отпечатки и перехватить медиа) нельзя
даже через взломанный сервер или канал. Медиа шифруется DTLS-SRTP.

**Почему Electron, а не Tauri.** Tauri на Windows использует системный WebView2, где нельзя
выбрать окно для захвата своим интерфейсом, зафиксировать UDP-порты WebRTC, включить флаги Chromium
(аппаратный AV1 для WebRTC выключен по умолчанию) и захватить системный звук. В Electron всё это есть.

## Быстрый старт

Обычный способ — готовый `DuoStream.exe`: без консоли, Node.js, npm и .NET у пользователей.

1. **Собрать один раз** на любом ПК с Node.js и .NET SDK 10 (подробно — [docs/01-install.md](docs/01-install.md)):

   ```powershell
   cd client
   npm install
   npm run dist
   ```

   В `client/dist` появятся `DuoStream-Setup-1.0.0.exe` (установщик, ярлык на рабочем столе) и
   `DuoStream-1.0.0-portable.exe` (один файл, без установки). Их и передайте второму участнику.
2. **Стример** запускает DuoStream → «Я стример» (галочка «Запустить сигнальный сервер в приложении»
   включена) → пароль → «Подключиться». Приложение покажет адрес для зрителя — передайте его и пароль.
3. **Зритель** запускает DuoStream → «Я зритель» → адрес и пароль → «Подключиться».

Настройки запоминаются, в следующий раз достаточно нажать «Подключиться». Порты на роутере стримера
приложение открывает само через UPnP (если он включён на роутере), иначе — ручной проброс:
[docs/02-port-forwarding.md](docs/02-port-forwarding.md).

**Обновления.** Каждый пуш в `master` собирает exe в GitHub Actions и публикует релиз
(`.github/workflows/release.yml`). Установленный DuoStream сам скачивает новую версию и ставит её при
выходе; portable-версия сообщает о новой версии и открывает страницу загрузки.

## Что проверено

Проверка шла на Windows 11 (сборка 26300), RTX 5070 Ti (к ней подключены оба монитора, на ней же
работает Chromium; встроенная графика Ryzen включена, но не используется), Electron 44.9.3 / Chromium 152.
Два экземпляра приложения работали на одном ПК через сигнальный сервер.

- Сигнальный сервер: 6 автотестов (`npm test`) — пара, пересылка, неверный пароль, бан, вытеснение, ошибки.
- **AV1 кодируется аппаратно**: `MediaFoundationVideoEncodeAccelerator (NVIDIA AV1 Encoder MFT)`,
  у зрителя аппаратное декодирование `D3D11VideoDecoder`, 2560×1440, без потерь.
- Битрейт: оценка канала стартует с ~10 Мбит/с и не опускается ниже заданных 8000 кбит/с; на
  динамичной картинке 15–17.5 Мбит/с. Без исправления (см. `sdp.js`) старт был ~2 Мбит/с.
- **Собственный захват, 120 FPS:** экран 2560×1440 — ~119 FPS кодирования на `NVIDIA AV1 Encoder MFT`
  и столько же у зрителя (аппаратное декодирование), копирование кадра ~0,2 мс, 30 секунд без пропусков;
  с масштабом до 1920×1080 — тоже ~120 FPS. Окно, меняющее размер, захватывается без искажения пропорций.
- Откаты на захват Chromium срабатывают: процесс захвата не собран, падает при запуске, убит во время
  трансляции; переключение способа захвата в настройках на лету. Закрытие захватываемого окна
  останавливает трансляцию. Системный звук при собственном захвате передаётся.
- Смена источника и рост окна не оставляют кодирование на CPU: Chromium при увеличении кадра уходит с NVENC
  на libaom, приложение пересоздаёт сессию (у окна — через ~1,5 с после ресайза).
- Шумодав DeepFilterNet3 (речь с шумом, `scripts/test-denoiser.mjs`): SI-SDR +9.6 дБ при SNR 5 дБ и
  +11.9 дБ при SNR 0 дБ (у DTLN +8.5 и +10.6); фон в длинной паузе ослаблен на 40 дБ (с −35 до −75 дБFS),
  с голосовым порогом — полная тишина, щелчки клавиатуры тоже; речь порог не обрезает (SI-SDR тот же).
  Задержка 30 мс, в приложении ~2 мс CPU на 10 мс звука, без пропусков.
- Горячие клавиши: переключение микрофона, режим рации (передача только при зажатой клавише,
  отключение через 150 мс после отпускания), назначение в настройках, шумодав — проверены нажатиями F22–F24.
- Собранный exe находит GitHub Releases для обновлений (до первого релиза отвечает «релизов нет»).
- Порты WebRTC ограничены диапазоном 50000–50019; кандидат «белый IP : порт» доходит до зрителя и принимается.
- **Собранный `DuoStream.exe`** (`npm run dist`): встроенный сервер поднимается из exe, зритель подключается,
  P2P устанавливается, собственный захват из ресурсов сборки даёт ~116 FPS на AV1 NVENC, шумодав работает;
  portable-версия запускается за ~3 с. В сборку попадает только шаблон настроек без пароля.

## Ограничения (честно)

- **120 FPS — только с собственным захватом.** Встроенный захват Chromium (запасной вариант) на
  Windows 11 24H2+ даёт не больше ~60 FPS. Причины измерены на тестовом ПК:
  1. Windows Graphics Capture по умолчанию отдаёт новый кадр не чаще раза в 16 мс
     (`MinUpdateInterval = 16 мс`) и только на границе обновления монитора: на 170 Гц это 17,65 мс,
     то есть 56,7 FPS. libwebrtc в Chromium это свойство не меняет. С `MinUpdateInterval = 1 мс`
     та же Windows отдаёт 170 FPS.
  2. Для экрана 1440p добавляется правило Chromium «захват не дольше 50% времени ядра»: один захват
     с копией в RAM и конвертацией занимает 9–10 мс, период кадра — 19–21 мс (~50 FPS).
- Собственный захват опирается на экспериментальный модуль Electron `sharedTexture` (Electron 44) и
  `MediaStreamTrackGenerator`; при обновлении Electron его нужно перепроверить. Процесс захвата —
  самодостаточный exe (~42 МБ), для сборки нужен .NET SDK 10.
- Если видеокарта загружена на 100% уже в момент старта трансляции, Chromium может сразу выбрать
  программный энкодер; приложение заметит это по статистике и через ~5 с пересоздаст сессию.
- Для 1440p при 120 FPS 20 Мбит/с — нижняя граница: в режиме «держать FPS» WebRTC при нехватке битрейта
  уменьшает кадр до 1080p. Для чёткого 1440p@120 ставьте 25–35 Мбит/с или режим «держать разрешение».
- DeepFilterNet3 — потоковый ONNX-экспорт из форка torchDF (официальный ONNX не потоковый). Модель весит
  16 МБ и занимает ~20% одного ядра CPU; если она не загрузится, включится лёгкая DTLN (16 кГц, голос глуше).
  Голосовой порог решает «говорит / молчит» по оценке SNR самой модели; очень тихую речь на громком фоне
  он может открывать с опозданием — тогда выключите его в настройках.
- Глобальные клавиши не видят нажатий в играх, запущенных от имени администратора (ограничение Windows),
  пока сам DuoStream запущен без прав администратора.
- Шумодав проверен на синтезированной речи (TTS Windows), а не на записи живого микрофона.
- NVENC не кодирует VP9: этот запасной вариант идёт на CPU. Аппаратный запасной — H.264.
- Системный звук захватывается с устройства по умолчанию в стерео и без звуков самого DuoStream
  (Chromium `restrictOwnAudio` → loopback с исключением своего процесса, Windows 10 2004+). Что голос
  зрителя действительно не попадает в захват, на тестовом ПК проверить не удалось: его устройство
  по умолчанию не отдавало звук в loopback.
- Статичное окно Windows Graphics Capture не обновляет: процесс захвата повторяет последний кадр
  10 раз в секунду, иначе потерянный ключевой кадр нечем восстановить.
- Реальный интернет-путь (два разных провайдера), STUN, TURN и сборка установщика на тестовом стенде
  не проверялись: STUN и загрузки с GitHub из Node там недоступны. Оба экземпляра работали на одном ПК,
  поэтому у зрителя декодирование конкурировало за ту же видеокарту (105–119 FPS вместо 120).
